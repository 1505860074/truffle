# Truffle 需求文档目录

## 文档说明

本文档是本目录的命名规范与索引，不是某个具体功能的实现说明。新增、重命名或废弃需求文档时，必须先阅读本文档并遵守其规则；修改后同步更新文末索引。命名规范优先于个人习惯，若确需例外，先在本文档「例外记录」中说明原因。所有文档内容使用中文，路径与目录名使用英文小写加连字符，避免中文路径在 Git、打包工具和跨平台环境中的编码问题。

## 目录结构

```
specs/
├─ README.md                         # 本文档：命名规范 + 索引
├─ SPEC-001-project-system/
│  └─ requirements.md
├─ SPEC-002-<slug>/
│  └─ requirements.md
└─ ...
```

## 命名规则

- 顶层目录固定为 `specs/`，所有需求文档都放在这里。
- 每个需求一个独立子目录，格式：`SPEC-<三位序号>-<slug>`。
  - `SPEC`：固定大写前缀。
  - 三位序号：`001`、`002`……只增不减，不复用，不跳号；超过 999 时自然扩展为四位。
  - `slug`：简短英文小写描述，单词之间用 `-` 连接，例如 `project-system`、`batch-export`、`ai-mask`。
- 目录内固定文件名按文档类型命名，不用中文、不加日期后缀：
  - `requirements.md`：需求规格（必须有）。
  - `design.md`：技术设计（可选）。
  - `tasks.md`：任务拆分（可选）。
  - `test-plan.md`：测试计划（可选）。
- 需求编号一经分配不可更改；需求废弃时保留目录，在索引中把状态改为「已废弃」，不要删除历史。
- 文档标题写在文件内（中文标题 + `文档编号` 元信息），不要依赖目录名表达完整含义。

## 状态取值

- `草稿`：正在整理，尚未与用户确认。
- `确认中`：主体需求已确认，仍有开放问题待确认。
- `已确认`：需求已全部确认，可以进入实现。
- `实现中`：正在开发。
- `已完成`：已实现并通过验收。
- `已废弃`：不再使用，保留供追溯。
